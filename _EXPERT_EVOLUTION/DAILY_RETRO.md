## 2026-11-23 · 基础设施日（人工注入的首个复盘基线）

### 一、数据回采（截至 02:40，实测）
| 指标 | 数值 | 说明 |
|---|---|---|
| 库规模 | **1218 组件 / 10,000** | Base154 / MathData294 / Algo135 / Device221 / Motion126 / Process288 |
| 文件一致性 | registry 1218 = .st 1218 | 孤儿 0 / 缺失 0，组件层完全对齐 |
| JSONL | **1252 条**（多 34 条） | 语料多于注册，疑历史轮次拒收件/重复条目未清理，待校准 |
| L2 通过率 | 40 件 100% / 120 件 88.3% | 修复前同批 75%（含 16 假阳性） |
| 单件编译耗时 | 2.25 秒 | 修复前 6.5 秒（接口预筛缓存生效） |

### 二、第一瓶颈
**存量代码缺陷密度**：120 件抽样 14 件失败（11.7%），按 1218 件外推约 **140 件存在真实编译缺陷**。
依据：失败类型集中在 6 类（E044/E032/E052/E007/E048/E089），非随机分布，属同一批生成时期的系统性写法问题。

### 三、三项优化（已生效）
1. **流程**：组件生命周期五步严格串行；本地 L2 编译强制串行（并行造假阳性）。
2. **专家定义**：编译验证工程师职责新增「工具链自愈四件套」（stub_fix / iface_stub_gen / reorder_methods / fix_end_method），并要求每轮开跑前自检。
3. **提示词**：新增红线 R8~R12（METHOD 位序与收尾、禁构造函数式转换、VAR 分号、ENUM 赋值符），已写入 automation prompt 阶段三。

### 四、架构效率评估
- 并行净收益：**负**。编译并行省 19% 时间（90s→73s），却引入 40% 假阳性（30 PASS→14 PASS），完全不可接受。
- 决策：**编译链永久串行**；并行只保留在「子代理角色层」（猎人∥编码）与「批内需求派发」两处，这两处不触及共享状态。

### 五、资源策略
- 已用免费云：GitHub Actions 跑 MatIEC（本地无 C 工具链，云端 ubuntu 现编 iec2iec）。
- 待评估卸载项：全库 L2 扫描（1218 件 × 2.25s ≈ 46 分钟，本地很重）→ 可搬 CI 并行 job，用 matrix 分库跑。
- 备选免费算力清单（需账号/密钥，未启用）：GitLab CI 400 分钟/月、Azure Pipelines（public 免费 10 并行 job）、AppVeyor（Windows 环境，可用于编 Windows 版 MatIEC）、Cirrus CI。

### 六、⬆ 已建议的指令变更
- [ ] 存量缺陷修复配额：若 L2 通过率 <85%，每轮预留 4 个名额修存量（已写入阶段一第 5 条，生效中）
- [ ] JSONL 与 registry 的 **34 条差额**需一次性校准（语料多于注册，疑拒收件未剔除），避免长期漂移
- [ ] 全库 L2 扫描改由 CI matrix 承担，本地只跑增量
